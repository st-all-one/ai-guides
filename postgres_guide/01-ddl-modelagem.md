## 1. Tipos de Dados — Escolhas Modernas

### Numéricos

| Tipo | Uso | Recomendação |
|------|-----|-------------|
| `smallint` / `int2` | -32k a +32k | Contadores pequenos, flags |
| `integer` / `int4` | -2B a +2B | **Padrão para IDs e contadores** |
| `bigint` / `int8` | ilimitado prático | IDs que podem crescer >2B |
| `decimal(p,s)` / `numeric(p,s)` | Exato, precisão arbitrária | **Sempre para dinheiro/financeiro** |
| `real` / `float4` | 6 dígitos decimais | Aproximações, raramente |
| `double precision` / `float8` | 15 dígitos decimais | Científico, medições |
| `money` | Moeda com locale | **🛑 Evitar** — problemas com arredondamento e locale |

```
✅ numeric(12,2) para valores financeiros
✅ bigint para IDs que podem escalar
✅ integer para a maioria dos casos
```

### Caracteres

| Tipo | Recomendação |
|------|-------------|
| `text` | **✅ Padrão moderno** — sem limite de tamanho, mesma performance que varchar |
| `varchar(n)` | Apenas quando há **requisito de negócio** para limitar tamanho |
| `char(n)` | **🛑 Evitar** — padding com espaços, sem vantagem real |

```
🔍 Na doc: "There is no performance difference among these three types."
Sempre use text a menos que o contrato exija varchar(n).
```

### JSON vs JSONB

| Tipo | Armazenamento | Índices | Preserva chaves duplicadas? | Whitespace |
|------|--------------|---------|----------------------------|------------|
| `json` | Texto puro (input preservado) | ✅ (via expression index) | Sim | Sim |
| `jsonb` | Binário decomposto | ✅ **GIN nativo** | Não (última vence) | Não |

**📝 Regra prática:**
- `json` apenas se você precisa preservar whitespace/chaves duplicadas (raríssimo)
- `jsonb` em **todos os outros casos** — permite indexação GIN, operadores `@>`, `?`, `?|`, `?&`

```
✅ jsonb + GIN index para queries em documentos
✅ jsonb_path_ops para performance em paths específicos
```

### Data/Hora

| Tipo | Precisão | Recomendação |
|------|----------|-------------|
| `timestamptz` | 1 microssegundo | **✅ Padrão absoluto** — armazena UTC, converte no fuso do cliente |
| `timestamp` | 1 microssegundo | **🛑** sem time zone — causa ambiguidade |
| `date` | 1 dia | ✅ Datas sem hora |
| `time` / `timetz` | 1 microssegundo | ✅ Horário fixo; timetz é raro |
| `interval` | 1 microssegundo | ✅ Durações entre eventos |

```
🔍 timestamptz NÃO armazena time zone — apenas normaliza para UTC internamente.
O time zone é aplicado na exibição (cliente ou AT TIME ZONE).
```

### UUID

```
✅ uuid DEFAULT gen_random_uuid()  — melhor que uuid_generate_v4() da extensão pgcrypto
✅ Usar sem hífen para storage? Apenas visual — internamente é uuid de 128 bits
```

### Arrays e Range Types

```
✅ integer[] para listas pequenas embutidas (evita tabela extra)
✅ daterange, tsrange para períodos com exclusão de sobreposição (exclusion constraints)
```

### Generated Columns (PG 12+)

```sql
CREATE TABLE pessoas (
    nome text,
    sobrenome text,
    nome_completo text GENERATED ALWAYS AS (nome || ' ' || sobrenome) STORED
);
```

**📝 Regras:**
- `GENERATED ALWAYS` — não pode ser escrito no INSERT/UPDATE
- `STORED` — única opção atual (VIRTUAL ainda não implementado)
- Expressão só pode usar colunas da mesma tabela, funções imutáveis

### Identity Columns (PG 10+) — **substitui SERIAL**

```sql
-- ✅ Moderno: IDENTITY
CREATE TABLE usuarios (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome text NOT NULL
);

-- ✅ Com ciclo e cache
CREATE TABLE pedidos (
    id bigint GENERATED BY DEFAULT AS IDENTITY
        (START WITH 1000 INCREMENT BY 1 CACHE 100) PRIMARY KEY
);
```

**📝 `GENERATED ALWAYS` vs `GENERATED BY DEFAULT`:**
- `ALWAYS` — usuário NÃO pode fornecer valor (erro se tentar)
- `BY DEFAULT` — usuário pode fornecer valor (se não fornecer, usa sequência)

**🛑 `SERIAL` é legado:**
```sql
-- ❌ Antigo
id SERIAL PRIMARY KEY

-- ✅ Moderno
id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```
Vantagens do IDENTITY: respeita GRANT de privilégios, não cria sequência separada visível, não permite bypass sem OVERRIDING.

## 2. Constraints — Padrão Moderno

### Primary Key e Unique

```sql
-- Sempre nomeie constraints
CONSTRAINT pk_usuarios PRIMARY KEY (id)
CONSTRAINT uq_usuarios_email UNIQUE (email)
```

### Foreign Keys

```sql
CONSTRAINT fk_pedidos_usuario
    FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
    ON DELETE RESTRICT     -- ou NO ACTION, SET NULL, CASCADE
    ON UPDATE CASCADE;     -- ✅ cascata para PK mutável
```

**📝 Recomendação:**
- `ON DELETE RESTRICT` ou `NO ACTION` para proteger integridade
- `ON DELETE CASCADE` apenas quando semanticamente correto (ex: pedido → itens)
- `ON DELETE SET NULL` quando a FK é opcional
- Sempre indexe FKs (o planner precisa para joins; o sistema não cria índice automático)

### Check Constraints

```sql
CONSTRAINT ck_salario_positivo CHECK (salario > 0)
CONSTRAINT ck_datas CHECK (data_inicio <= data_fim)
```

**📝 Dica:** CHECK constraints são a forma MAIS EFICIENTE de validar dados — operam no mesmo nível do storage, sem overhead de trigger ou aplicação.

### Exclusion Constraints (PG 9+)

```sql
CREATE TABLE reservas (
    sala integer,
    periodo tsrange,
    EXCLUDE USING gist (sala WITH =, periodo WITH &&)
);
```

**📝** Impedem sobreposição de intervalos — único constraint que usa operador `&&` (overlap).

## 3. Particionamento (Declarative Partitioning — PG 10+, melhorado no PG 12+)

### Estratégias

```sql
-- RANGE: por faixa de valores
CREATE TABLE logs (
    criado_em timestamptz NOT NULL,
    mensagem text
) PARTITION BY RANGE (criado_em);

-- LIST: por valor discreto
CREATE TABLE clientes (
    id integer, regiao text
) PARTITION BY LIST (regiao);

-- HASH: distribuição uniforme (PG 11+)
CREATE TABLE eventos (
    id bigint, payload jsonb
) PARTITION BY HASH (id);
```

### Criando partições

```sql
CREATE TABLE logs_2026_q1 PARTITION OF logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');

CREATE TABLE clientes_norte PARTITION OF clientes
    FOR VALUES IN ('NORTE');

CREATE TABLE eventos_0 PARTITION OF eventos
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
```

### 📝 Práticas recomendadas

1. **Subpartitioning**: possível mas aumenta complexidade — evite mais de 2 níveis
2. **Índices**: crie índices na tabela particionada — propagam automaticamente
3. **FKs**: tabela particionada pode referenciar PK de tabela não-particionada; o inverso é limitado
4. **UPDATE que move partição**: possível (row movement implícito), mas caro
5. **Detach + attach** para operações de manutenção rápidas:

```sql
ALTER TABLE logs DETACH PARTITION logs_2025_q4;
-- operações offline na partição
ALTER TABLE logs ATTACH PARTITION logs_2025_q4
    FOR VALUES FROM ('2025-10-01') TO ('2026-01-01');
```

## 4. Domínios (Domains)

Domínios criam tipos reutilizáveis com constraints embutidas:

```sql
CREATE DOMAIN email_valido AS text
    CHECK (VALUE ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$');

CREATE TABLE contatos (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email email_valido NOT NULL
);
```

**📝** Úteis para padronizar validações em múltiplas tabelas.

## 5. Schema Design — Organização

```sql
CREATE SCHEMA IF NOT EXISTS comercial;
CREATE SCHEMA IF NOT EXISTS financeiro;
```

**📝** Use schemas para organizar módulos — não use o schema `public` para tudo.

## 6. Herança de Tabelas (Table Inheritance)

```sql
CREATE TABLE cidades (
    nome text, populacao real, altitude integer
);
CREATE TABLE cidades_capital (
    estado char(2)
) INHERITS (cidades);
```

**⚠️** Herança de tabelas é **diferente** de herança de objetos. Não é substituta para partitioning. Tem semânticas surpreendentes (índices não são herdados, FKs problemáticas). **Preferir particionamento declarativo.**

## 8. Armadilhas Comuns em DDL

| 🛑 Antipadrão | Problema | ✅ Solução |
|---------------|----------|-----------|
| `SERIAL` | Não respeita GRANT, sequência pública | `GENERATED AS IDENTITY` |
| `varchar(255)` sem motivo | Falso senso de limite, sem gain | `text` + CHECK se precisar limitar |
| `float` para dinheiro | Arredondamento cumulativo | `numeric(15,2)` |
| `timestamp` sem tz | Ambiguidade de fuso horário | `timestamptz` |
| `json` para consultas | Performance baixa, sem índices | `jsonb` + GIN |
| `char(n)` | Padding, sem vantagem | `text` ou `varchar` |
| Tabela sem PK | Impossível replicar logicamente, performance pobre | Sempre `GENERATED AS IDENTITY PRIMARY KEY` |
| FK sem índice | Deadlocks em UPDATE/DELETE na PK referenciada | Indexar toda FK |
| Particionamento em tabela com FKs de referência | Limitações operacionais | Planejar antes |
